# 日志到档案

把 `data/journal/` 里的日志蒸馏成 `data/profile/` 里的元工程档案。档案体裁以 profile 仓的 CONTRIBUTING 为准，本文件只约定提炼方法与分流规则。

## 先分流：哪些进档案

日志是素材，不是每条都进档案。先问一句：**这条是「反复出现的结构」，还是「一次具体的事」？**

| 日志里的东西 | 去哪里 |
|:--|:--|
| 反复出现的判断方式、边界、模式（跨日期稳定） | **profile**（档案） |
| 一次具体的事、某个项目的状态 | 留在 journal，不进档案 |
| 某个领域的具体做法、规范、交付物（**答案**） | 回该领域自己的仓，不进元工程 |
| 说不清、还在争的说法（**问题**） | 进 profile 或 insight，在元工程里分解 |

后两条与 `meta-align` 的分界一致：**元工程管问题，领域管答案。**

## 两种档案体裁（以 profile 仓 CONTRIBUTING 为准）

1. **元认知快照**：一副骨架（范畴、层级、关系与约束）+ 它各主体上的部署。只放当前最新一份，更新时替换不并存。
2. **四步档案**：一个问题怎么被拆开——业务意图、哲学阐述、数学实现、代码实现。文件名与标题围绕业务场景本身，不用方法词。

## 原则

- **单位是线索，不是日期文件**。一条线索可跨多篇日志，一篇日志可贡献多条线索，多对多。
- **只收跨时间稳定的**。单次事件、临时状态、待定决策不进档案。
- **每条带出处**。档案条目要能指回日志：哪个域、哪一天、哪句话。没有出处的结论是评论，不是档案。
- **改写而非追加**。已有线索就地更新，重复的删掉，重复的合并；日记体里两个日期其实是一件事，合成一条。
- **档案不给建议**。建议是给人的输出，不是档案内容。
- **少而准 > 全**。over-merge 比 under-merge 危险：宁可留两条相邻线索，也不要把它们焊成一条假的。

## 流程

1. **扫描**：按域通读 `data/journal/<域>/`。`default/` 是未分类的默认入口，先看它能不能落域。总量可能上百篇、跨三十多个域——**分域分批做，不要一次通读**。
2. **过滤**：按上表分流，把「答案」退回领域，把「问题」留下。
3. **聚类**：同一线索跨日期、跨域合并；判断依据是本质相同，不是措辞相似。
4. **蒸馏**：剥掉具体项目名、工具名、业务细节，留下结构本身。
5. **合并**：读现有档案，新线索新增一节，已有线索改写，重复的合并。
6. **落点**：元认知类的进 `data/profile`；只到洞察层的进 `data/insight`；属于某个领域的问题先回该领域，仍说不清的留在 `data/context` 待人确认。

## 边界

- 日志里没有的，不编。
- **骨架只能在元工程层改**：范畴的条数、层级、四条关系的语义——领域侧只能换类名（见 `meta-align`）。
- 拿不准的进 `data/context` 草稿箱，人确认后再进正式仓，不留副本。
- 快照式更新要写清取代了什么：被换掉的那份留来源仓与日志，不做版本堆叠。

## 输出

档案文件的结构以 profile 仓的 CONTRIBUTING 为准；本技能保证的是：来源可查、线索可并、出处不丢。
